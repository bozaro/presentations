Контейнеры и виртуальные машины

Сервисы и физическое железо

Обычно физический сервер слишком большой для одного экземпляра сервиса.

Есть потребность запускать несколько разных сервисов на одном физическом сервере.

Сервер xFusion 1288H V7 8SFF (1U)

  • CPU 2x Intel Xeon Gold 6430 (32C 60M Cache 2.10 GHz)
  • RAM 12x 64GB DDR5 RDIMM 4800MHz
  • HDD 2x SSD 480GB SATA 2,5" (до 8 HDD 2.5'' SFF)

Итого: 64 ядра (128 потоков исполнения) и 768GB RAM

Несколько сервисов на одном сервере

Технически можно установить несколько сервисов на одном сервере.

  • Общая операционная система, которую очень больно обновлять
  • Проблема изоляции ресурсов
  • Проблема общих зависимостей
  • Проблема воспроизводимости окружения

Какие пути решения?

Виртуализация

Внутри гипервизора запускаем несколько виртуальных хостов.

Каждый виртуальный хост притворяется физическим хостом.

Контейнеризация

Внутри операционной системы приложения изолируются в отдельных контейнерах.

Каждый процесс контейнера является обычным процессом операционной системы.

Виртуализация

Важно

  • Диск - блочный файл/устройство

Плюсы

  • Можно запустить другую операционную систему (например Windows, Linux или FreeBSD)
  • Высокая степень изоляции
  • Можно эмулировать другую архитектуру (например PlayStation 2)

Минусы

  • Высокие накладные расходы

Контейнеризация

Важно

  • Диск - каталог на хостовой машине

Плюсы

  • Минимальные накладные расходы

Минусы

  • Общее ядро операционной системы
  • Более слабая изоляция ресурсов (например: общий дисковый кэш)

Docker

Контейнеры существуют очень давно, но до Docker-а не было простой инфраструктуры для работы с контейнерами.

Docker предоставил законченное решение для:

  • Сборки контейнеров
  • Обмена и переиспользования контейнеров
  • Запуска контейнеров

Docker-контейнеры поддерживают операционные системы:

  • Linux
  • Windows

Docker-образ

git clone https://github.com/docker/docker-gs-ping .
docker build --tag docker-gs-ping .

Dockerfile

# syntax=docker/dockerfile:1
FROM golang:1.19
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY *.go ./
RUN CGO_ENABLED=0 GOOS=linux go build -o /docker-gs-ping
EXPOSE 8080
CMD [ "/docker-gs-ping" ]
https://docs.docker.com/guides/golang/build-images/

Docker-образ (multistage)

git clone https://github.com/docker/docker-gs-ping .
docker build --tag docker-gs-ping -f Dockerfile.multistage .

Dockerfile.multistage

# syntax=docker/dockerfile:1
FROM golang:1.19 AS build-stage
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY *.go ./
RUN CGO_ENABLED=0 GOOS=linux go build -o /docker-gs-ping

FROM gcr.io/distroless/base-debian12 AS build-release-stage
WORKDIR /
COPY --from=build-stage /docker-gs-ping /docker-gs-ping
EXPOSE 8080
USER nonroot:nonroot
ENTRYPOINT ["/docker-gs-ping"]

Кэширование сборки docker-образов

Не правильно

RUN apt update
RUN apt install -y golang

Правильно

RUN apt update && apt install -y golang

Оптимально

RUN --mount=type=cache,sharing=private,target=/var/cache/apt \
    --mount=type=tmpfs,target=/tmp \
    apt update && apt install -y golang && apt-get clean all

Что внутри образа?

Подведём итоги

  • OCI Image — вырос из Docker Image и является его развитием
  • Сборки порождают слои, каждый из которых используется только для чтения (overlayfs)
  • OCI Image содержит метаданные: переменные окружения, команда выполнения, порты и т.п., которые используются как значения по-умолчанию при запуске контейнера
  • В контейнер можно передавать конфигурацию через модификацию переменных окружения и монтирования каталогов/файлов при его запуске

Что такое Pod?

  • Pod — один или несколько контейнеров, совместно запускаемых на одной ноде.
  • Общая сеть: у Pod-а один IP, контейнеры видят друг друга через localhost.
  • Общие тома: том описывается на уровне Pod-а и монтируется в контейнеры.
  • Общие пространства имён Linux (сеть, hostname) удерживает сервисный контейнер pause.
https://kubernetes.io/docs/concepts/workloads/pods/

Несколько контейнеров в Pod-е

Sidecar-паттерн: приложение + сборщик логов

apiVersion: v1
kind: Pod
metadata:
  name: app-with-sidecar
spec:
  containers:
  - name: app
    image: nginx:1.14.2
    volumeMounts:
    - name: logs
      mountPath: /var/log/nginx
  - name: log-shipper
    image: fluent/fluent-bit
    volumeMounts:
    - name: logs
      mountPath: /data
  volumes:
  - name: logs
    emptyDir: {}

Кто в ноде запускает контейнеры?

  • Pod-ы запускает kubelet на ноде — через CRI (Container Runtime Interface) он обращается к контейнерному runtime.
  • Runtime качает образы и создаёт контейнеры: containerd или CRI-O; низкоуровневый запуск делает runc по OCI-спецификации.
  • Docker внутри Kubernetes больше не используется: dockershim удалён из Kubernetes 1.24 (2022).
  • Образы, собранные docker build, продолжают работать — стандарт OCI-образа общий.
https://kubernetes.io/docs/setup/production-environment/container-runtimes/

Откуда берётся образ?

image: nginx:1.14.2 ⇒ docker.io/library/nginx:1.14.2: runtime скачивает его из container registry.

  • Публичные реестры: Docker Hub, ghcr.io, registry.k8s.io.
  • Приватные: Yandex Container Registry, Harbor, реестр GitLab; доступ — через imagePullSecrets.
docker build --tag my-app:1.0 .
docker tag my-app:1.0 registry.example.com/my-app:1.0
docker push registry.example.com/my-app:1.0

Rolling update

При изменении template Pod-а Deployment постепенно заменяет Pod-ы новой версией.

spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  • maxSurge — на сколько Pod-ов можно превысить число реплик.
  • maxUnavailable — сколько Pod-ов может недостаать.
  • Новый Pod считается готовым только после прохождения readinessProbe.
https://kubernetes.io/docs/concepts/workloads/controllers/deployment/

Управление выкаткой

Обновляем образ

kubectl set image deployment/nginx nginx=nginx:1.25.3

Следим за прогрессом

kubectl rollout status deployment/nginx
kubectl rollout history deployment/nginx

Откатываемся, если что-то пошло не так

kubectl rollout undo deployment/nginx

Rollout restart

rollout restart меняет аннотацию kubectl.kubernetes.io/restartedAt в Pod template — Deployment делает rolling update без смены образа.

kubectl rollout restart deployment/nginx
kubectl rollout history deployment/nginx
  • Зачем: Pod-ы не перезапускаются сами при изменении ConfigMap / Secret.
  • Зачем: пересоздать зависшие Pod-ы, не меняя манифест.
  • Свойства те же, что у rolling update: maxSurge, maxUnavailable, readinessProbe.
  • Есть у deployment, daemonset, statefulset.
https://kubernetes.io/docs/reference/kubectl/generated/kubectl_rollout/kubectl_rollout_restart/

Rollback Deployment

Каждая ревизия — это ReplicaSet, который Deployment сохранил (по умолчанию 10 последних).

Смотрим историю и катимся назад

kubectl rollout history deployment/nginx
kubectl rollout history deployment/nginx --revision=3
kubectl rollout undo deployment/nginx --to-revision=3

Если выкатка застряла

kubectl rollout status deployment/nginx   # ждём завершения, есть --timeout
kubectl rollout undo deployment/nginx      # откат к предыдущей ревизии
  • undo — тоже rolling update: новые Pod-ы проходят readiness.
  • Нельзя откатиться на ревизию, удалённую вместе с ReplicaSet.
  • spec.revisionHistoryLimit — сколько ревизий хранить.
https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#rollback

Указываем, какие ресурсы нужны Pod-ам

  • У контейнеров Pod-а задаются requests и limits.
  • Значение requests учитываются при выборе ноды, на которую будет помещаться Pod.
  • Значение limits задаёт лимиты потребления. Оно не учитывается при выборе ноды, на которую будет помещаться Pod.
  • Из коробки есть ресурсы: cpu, memory, ephemeral-storage, hugepages-<size>
  • requests/limits задают QoS-класс Pod-а (Guaranteed, Burstable, BestEffort) — по нему определяется, кого первым вытеснят (eviction) при нехватке ресурсов.
  • Приоритет Pod-а задаётся отдельно через priorityClassName.

Указываем, какие ресурсы нужны Pod-ам

apiVersion: v1
kind: Pod
metadata:
  name: pod-resources-demo
spec:
  containers:
  - name: app
    image: my-app:1.0
    resources:
      limits:
        cpu: "1"
        memory: "200Mi"
      requests:
        cpu: "1"
        memory: "100Mi"

Выбор ноды: nodeAffinity

  • Ноды помечаются labels-ами, а Pod просит подходящую ноду.
  • Самый простой способ — nodeSelector: точное равенство метки.
  • nodeAffinity — выражения (In, NotIn, Exists) и два уровня строгости: required... и preferred....
  • Так же отделяют и сами Pod-ы: podAntiAffinity.
https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/

nodeAffinity: пример

required — иначе Pod не запланируется

requiredDuringSchedulingIgnoredDuringExecution:
  nodeSelectorTerms:
  - matchExpressions:
    - key: gpu
      operator: In
      values: ["a100"]

preferred — мягкое пожелание с весом

preferredDuringSchedulingIgnoredDuringExecution:
- weight: 1
  preference:
    matchExpressions:
    - key: zone
      operator: In
      values: ["zone-a"]

Разнос Pod-ов по зонам

  • Защита от «вся копия приложения в одной зоне отказа».
  • topologyKey — label ноды, задающий домен: topology.kubernetes.io/zone или kubernetes.io/hostname.
  • maxSkew — допустимая разница Pod-ов между самой полной и самой пустой зоной.
  • DoNotSchedule — жёстко, ScheduleAnyway — мягко.
https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/

topologySpreadConstraints: пример

spec:
  replicas: 6
  template:
    spec:
      topologySpreadConstraints:
      - topologyKey: topology.kubernetes.io/zone
        maxSkew: 1
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app.kubernetes.io/name: nginx

PodDisruptionBudget

  • Страховка на время обслуживания кластера: kubectl drain не уронит реплики ниже лимита.
  • minAvailable или maxUnavailable — число или процент.
  • От невольных потерь (сбой ноды, eviction из-за нехватки ресурсов) не защищает.
  • Однорепличному приложению ставят minAvailable: 0, иначе drain ноды зависнет.
https://kubernetes.io/docs/concepts/workloads/pods/disruptions/

PodDisruptionBudget: пример

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: nginx
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: nginx

Обслуживание ноды — автоматика учтёт бюджет

kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data

HorizontalPodAutoscaler

  • Сам меняет число реплик Deployment/StatefulSet под нагрузкой.
  • Нужен metrics-server; процент считается от requests — поэтому их надо указывать.
  • Кроме ресурсов — custom и внешние метрики (например, глубина очереди через KEDA).
  • Окна стабилизации и скорость изменения настраивает behavior.
https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/

HorizontalPodAutoscaler: пример

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

Контроль жизненного цикла

Для определения состояния Pod-а есть следующие "пробы":

readinessProbe
Готов ли Pod принимать пользовательскую нагрузку?
livenessProbe
Жив ли Pod?
Если Pod не живой, то его удалит автоматика
startupProbe
До завершения старта сервиса к нему не применяются readinessProbe и livenessProbe

Долго стартующие приложения причиняют боль страдание.

Контроль жизненного цикла

apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    ports:
    - containerPort: 80
    readinessProbe:
      httpGet:
        path: /
        port: 80
      periodSeconds: 3

Конфигурация внутри Pod-а

apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx:1.14.2
    command: ["nginx", "-g", "daemon off;"]
    env:
    - name: FOO
      value: "bar"
    - name: MY_POD_NAME
      valueFrom:
        fieldRef:
          fieldPath: metadata.name
    ports:
    - containerPort: 80

Требования Kubernetes к приложению

Оркестратор не спрашивает разрешения: Pod-ы перезапускаются, переезжают и удаляются в любой момент — rolling update, HPA, kubectl drain, eviction, OOMKill, не прошедший livenessProbe контейнер.

  • Быстрый старт. Готовность за секунды: тяжёлые миграции и прогрев — в отдельный Job, медленный старт прикрывает startupProbe.
  • Умение завершиться в любой момент. Реагировать на SIGTERM, договорить начатые запросы, не хранить состояние внутри Pod-а.
  • Перечитывание секретов из файла. kubelet молча обновляет файлы в volume; значения из env не обновляются никогда. Либо перечитываем, либо делаем kubectl rollout restart.
  • Один процесс на контейнер. Тут нет systemd: процессу достаётся PID 1 и все сигналы, поэтому он не должен превращаться в демона (daemon off;).
  • Занимать ровно свой контейнер. Пулы потоков, кэши и GOMAXPROCS считать от requests/limits, а не от ресурсов ноды — иначе throttling и OOMKill.
https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/

Как правильно завершаться

Что делает kubelet

# 1) SIGTERM процессу, 2) ждёт terminationGracePeriodSeconds, 3) SIGKILL
# preStop-хук выполняется ДО SIGTERM
spec:
  terminationGracePeriodSeconds: 30
  containers:
  - name: app
    image: my-app:1.0
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "sleep 5"]
  • sleep в preStop нужен, чтобы Pod-ы успели исчезнуть из Endpoint-ов Service — иначе на rolling update ловим 502.
  • Обёртка CMD start.sh в Dockerfile перехватывает сигналы: PID 1 обязан пробрасывать их дальше (exec-form, sh -c "exec ...", tini).
  • По SIGTERM: перестать принимать соединения, доработать начатые, закрыть брокеры и пулы. SIGKILL догнать нельзя.
  • Граньтайм не спасает при OOMKill и сгоревшей ноде — состояние держим вне Pod-а, идемпотентность восстановления обязательна.
https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/

Service

  • Service работает на уровне L4: балансировка по IP и порту.
  • Pod-ы сервиса определяются через selector.
  • Service по умолчанию "видит" только READY Pod-ы.

  • Service создаёт DNS-записи:
    • A/AAAA
      srv.namespace.svc.cluster-domain.example
      nginx.default.svc.cluster.local
    • SRV
      _port-name._protocol.srv.namespace.svc.cluster-domain.example
      _http._tcp.nginx.default.svc.cluster.local

Ingress

  • Ingress работает на уровне L7 с HTTP-протоколом.
  • Pod-ы сервиса определяются через Service.
  • В кластере может быть несколько видов Ingress (ingressClassName)

Gateway API — развитие Ingress

  • Официальный преемник Ingress: маршрутизация описывается набором ресурсов.
  • Разделение ролей: Gateway настраивает платформа, HTTPRoute добавляет команда приложения.
  • Сопоставление по пути и заголовкам, фильтры, весовое распределение трафика (canary).
  • HTTP и gRPC — GA. Новые проекты лучше начинать с Gateway API.
https://gateway-api.sigs.k8s.io/

Gateway API: пример

Точка входа от платформы

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: nginx-gateway
spec:
  gatewayClassName: nginx
  listeners:
  - name: http
    protocol: HTTP
    port: 80

Маршрут от команды приложения

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: nginx
spec:
  parentRefs:
  - name: nginx-gateway
  hostnames:
  - "nginx-example.test"
  rules:
  - backendRefs:
    - name: nginx
      port: 80

Подведём итоги

  • Ресурсами управляет Deployment
  • Конфигурацию можно задать через ConfigMap и переменные окружения
  • Обязательно надо прописывать requests для Pod-а
  • Обязательно надо прописывать livenessProbe, readinessProbe и startupProbe
  • Для адресации между Pod-ами используются Service
  • Для доступа снаружи Kubernetes-кластера используются Ingress / Gateway API

Что осталось за кадром?

  • Состояние в Kubernetes: StatefulSet, Persistent Volume
  • VPA — вертикальное автомасштабирование (автоматическая подстройка requests)
  • NetworkPolicy и RBAC — сетевая изоляция и разграничение доступа

Deploy

Откуда берутся ресурсы для Kubernetes?

При раскатке приложений ресурсы для Kubernetes обычно генерируются автоматически.

Применение ресурсов через kubectl apply имеет существенный недостаток: никто не удаляет более ненужные ресурсы.

Стандартом де-факто для создания "приложений" в Kubernetes является Helm

Helm

Helm — менеджер пакетов для Kubernetes, который упрощает установку, обновление и управление приложениями в кластере. Особенность — использование чартов (Helm Charts) — стандартизированных пакетов, в которых содержатся все необходимые ресурсы и конфигурации.

Шаблонизатор Helm

apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-configmap
data:
  myvalue: "Hello World"

Внутри Helm использует шаблонизатор Go Template с набором дополнительных функций (в том числе go-spew).

Одна из проблем такого подхода: шаблонизатор работает с Yaml на уровне текста.
